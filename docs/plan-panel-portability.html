一、Cloudflare 保留与否：优缺点对照

保留（DNS 指向 CF，橙云代理，源站在 VPS）

优点说明
隐藏源站 IP扫描与攻击打在 CF 上，看不到你 VPS 的真实地址——这是最实际的一条
免费 DDoS / WAF 兜底面板是公网登录页，被爆破与被小流量打到死是常见事故，CF 能挡第一层
证书零维护CF 边缘证书自动续期；源站用 Cloudflare Origin Certificate，不用折腾 ACME
DNS 秒级切换源站顺位接管就是改一条 A 记录，配合低 TTL 生效很快
不消耗 Workers 请求额度只做代理时不调用 Worker，等于把控制面搬走后顺手解决了额度问题
可加访问限制WAF 规则能按国家/ASN/路径限制，单人使用的面板可以直接锁到“只允许你的常用地”
缺点说明与缓解
多一跳延迟CF→源站加 10–40ms；面板是管理台，感知很小。不影响代理流量（节点直连不经过面板）
CF 仍是入口单点CF 全站故障概率极低，但一旦发生面板进不去。缓解：保留一条“直连源站 IP+端口”的应急入口（仅自己知道）
必须正确配置源站防火墙只放行 cloudflare.com/ips 段，否则隐藏 IP 形同虚设；进阶用 mTLS（Authenticated Origin Pull）
排障多一层出问题要判断是 CF 规则/缓存还是源站。我们已踩过：opencode.ai 证书劫持、边缘仍接受 TLS 1.0
账号风险这是你真正的顾虑（GitHub 被封过）。缓解：域名 DS/A 记录备份、zone 配置定期导出、开 2FA；CF 不会因“fork/自用”封号，风险性质与 GitHub 不同

不保留（VPS 直接对外）

优点：链路短、排障简单；没有 CF 账号/规则/额度这一层；上传与长连接无额外限制。
缺点：源站 IP 暴露，被扫描/被 DDoS 就直接打到你机器；证书要自己上（到期忘续就全家掉）；没有就近加速；公网单 IP 的爆破压力全在自己身上。

结论：保留 CF。它带来的“隐藏 IP + 免费证书 + DDoS 兜底”对单人面板几乎是纯收益，代价只有一跳延迟和排障多一层。 真正的风险点是“CF 账号”，用备份与 2FA 对冲，而不是靠放弃 CDN 来对冲。

二、顺位接管：怎么让“一崩就上二”真的成立

难点不在于“切 DNS”，而在于谁来判定主控已死。如果让每台候选机自己判断，两台会同时认为自己是主控——这就是脑裂，比不切换更糟。

选定方案：Cloudflare Worker 当唯一仲裁者

每 60 秒：GET https://hk.example/health   （由 CF Worker 发起，只看这一个地址）

连续失败 3 次（≈3 分钟）
  → 读顺位表 [hk, jp, vn]
  → 把 DNS 记录从 hk 改为顺位里第一台“自检通过”的候选机
  → 同时写 epoch+1 到 D1（用于防脑裂）
  → 给该候选机下发“提升为主控”的信号（它自己的 watchdog 轮询 D1 的 epoch）

主控恢复后：不自动回切，只在面板上亮一条提示，由你点一下才切回

为什么这样最稳：仲裁者只有一个（CF），它看到的是“外网视角”，不会被单机网络抖动骗到；顺位表、epoch、当前主控全部是数据库里的一行，可读可改可审计。

防脑裂：epoch 代次

每台候选机的控制面启动时读取 meta.control_epoch 与自己保存的副本比较：自己落后就不允许以主控身份启动，只能当只读镜像。这样“被降级的主控重启后抢回去”这条最常见的脑裂路径被堵死。

必须接受的取舍：自动接管的判定是“连续 3 分钟不可达”，所以真实的切换窗口是 3–6 分钟，期间面板不可用（但代理流量不受任何影响）。 如果你的场景是“宁可手动也别切错”，把开关设成人工确认即可——方案里两者都保留，一个配置项切换。

顺位表长这样（面板可改，无需改代码）

顺位节点角色说明
1hk主控（primary）常驻运行控制面，对外域名指向它
2jp待机（standby）每分钟同步一次数据，随时可被提升

三、一键接入新机器

面板「添加服务器」填个名字，直接给出一条命令（token 一次性、30 分钟有效、绑定该节点记录）：

curl -fsSL https://panel.example.com/install.sh -o /tmp/sui.sh \
  && sha256sum /tmp/sui.sh \
  && bash /tmp/sui.sh --token ub_7Fk2…  --panel https://panel.example.com

脚本做四件事，全部幂等（重复执行不会破坏已有环境）：

  1. 检测发行版与架构，缺依赖则装（curl、systemd 必需项）
  2. 下载 agent 与内核（走面板静态分发，机房速度，不走你的家宽上行）
  3. 写 systemd 单元与 /etc/sui-agent.env，启动并等首轮心跳
  4. 回执给面板：成功则自动创建默认入站、生成订阅并回填到面板页面

退役同理：面板里点“退役”，该节点从聚合订阅中移除、agent 停止上报，机器本身不做任何破坏性操作（你想留着跑别的随时可以）。

shim 必须抹平的 5 个差异（已定实现方式）

#差异处理
1D1 接口是异步的，better-sqlite3 是同步的shim 内部同步执行，对外返回 Promise，调用方零改动
2.all()：D1 返回 {results, meta}，better-sqlite3 返回数组统一包装成 D1 形状（db.ts 的 all() 取的是 .results）
3.first() 在 better-sqlite3 里叫 .get()shim 提供 first()，内部转发 get()
4.run() 返回 meta.changes / meta.last_row_id映射 changes / lastInsertRowid，保留 meta.last_row_id（agent.ts 用到一处）
5batch() 在 D1 里隐式事务shim 用显式事务包裹，返回同形状数组
P0 结论：无障碍项。移植工作量集中在运行时外壳（约 300 行 shim + 一个 Node 入口），业务代码不需要改。 这让 P1 的风险从“可能要改业务逻辑”降到“只需保证 shim 语义对齐”。

为什么要分片：Cloudflare 静态资源单文件上限 25 MiB，agent 的 gz 约 25–33MB，单文件发布会被拒。 脚本里 fetch_parts 会读 .parts 循环下载再拼接，最后校验的是拼接后的整包。

聚合订阅的实际价值

客户端只保存 /sub/all 一个地址：新增节点 → 刷新多几条；退役节点 → 刷新少几条。 换服务器、跑路、不续费，都不需要再给任何客户端重发链接——这正是你最初提的那个痛点。
