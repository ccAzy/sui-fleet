一句话结论：骨架是好的，堆放是乱的。控制面/数据面分离、pull 模型、双运行时可移植这些架构决策都站得住； 真正拖后腿的是三件事——没有运行时校验层、没有静态检查配置、两个上帝文件。这三样都不是"重写"能解决的，是日常纪律。

架构

站得住的三件事

  • 控制面与数据面分离，节点只 pull：面板永远不主动连节点，节点挂了自己重试，面板换机只需改地址。这个决定让"面板在 Cloudflare / 面板在 VPS / 面板换机器"三次迁移都没动过节点侧逻辑。
  • 双运行时共享业务代码：apps/selfhost/src/d1.ts 用 node:sqlite 实现 D1 的子集，同一份 panel/src 在 Worker 和 Node 上跑。代价是垫片必须保持"语义等价"，一旦 D1 加了特性就要同步。
  • 变更靠 revision + 内容指纹双保险：revision 说"变过几次"，指纹说"现在是什么"。只有后者能发现"恢复备份 / 手改库 / 待机 promote"造成的漂移。

该拆的地方

  • panel/src/objects.ts（672 行）同时负责：对象 CRUD、客户端链接重算、默认配置种子、级联删除+审计、配置指纹投影。P1建议按职责拆成 objects/crud.ts、objects/links.ts、objects/lifecycle.ts。
  • 路由层直接写 SQL（api-read.ts 里 20+ 条内联查询）。P2不是错，但让"同一个查询在两处略有不同"这类 bug 无法避免（本轮就修过一次类似的）。
  • 没有领域错误类型。P1所有失败都是 json(c, null, new Error("中文句子"))，前端只能靠文案分支，无法做"未登录 vs 权限不足 vs 业务拒绝"的差异化处理。

类型边界

  • unknown 出现 112 次、any 13 次，集中在 objects.ts／api-read.ts／clash.ts。根因不是懒，是没有运行时校验层：请求体、备份文件、节点上报都是"先当 unknown 收下，再到处 typeof"。P1引入 zod/valibot 在边界一次性 decode，能让这 112 处里的大半消失，同时把"脏输入"挡在业务层之外。
  • 13 处 any 里最该改的是 http.ts 的 c: any（Hono Context 没写泛型），它让每个 handler 都失去类型保护。

工程化缺口

  • 仓库内没有 eslint / biome 配置。现在所有 lint 都来自我这边的 pi-lens，别人 clone 下来是零检查。P0加一份 biome.json（快、零配置冲突）比 eslint 更符合这个仓库的现状。
  • apps/selfhost 的 devDependencies 本地未安装，导致类型检查报 56 个"假错误"（process 未定义之类）。已在本轮 npm install 后归零，但应在 README 写明"三个包各自要 npm i"。
  • CI 有 typecheck + unit，但没有覆盖率门槛，也没有"产物大小"这类回归门禁（agent 二进制曾因此翻车）。

设计

  • 做得好：仪表 → 曲线 → 明细 → 趋势，信息密度递增；壁纸只铺底色、纸面保持不透明；对比度门禁取最亮格计算。这些是"看得见的设计"，不是样式堆砌。
  • Settings.vue 1037 行、20+ 个字段平铺在一页。P2按"面板自身 / 节点 / 订阅 / 安全"分组折叠，比加 tab 更省点击。
  • Cloud 模式下有 17 个字段是无效的（web 端口、证书路径等），保存仍会触发一次下发。P1用运行时能力探测决定显隐，而不是靠文档说明。
  • 新增的趋势块用的是同一套纸账本语言（细线、无卡片、无图例框），和首页其它部分一致——这是有意的，新功能不该长成另一个产品。
